# Persona preference embedding data model

## Purpose

Represent each persona as a collection of explicit concepts. Each preference has a kind, signed affinity, and concept embedding. Kind vectors are stored once in an identity-level map, keeping the identity property file self-contained and portable.

Embeddings identify semantic relatedness; signed affinity says whether that related concept attracts or repels the persona. These are separate signals.

The two sample identity profiles currently use synthetic vectors for matcher simulations. They are deterministic, rule-based test data, not embeddings generated by a trained model.

## Hierarchy

```text
Identity
  -> Kind vectors
  -> Persona
      -> Preference
          -> Keyword or phrase
          -> Kind reference
          -> Signed affinity
          -> Concept embedding
```

## Preference model

```json
{
  "keyword": "Australian rules football",
  "kind": "interest",
  "affinity": 0.9,
  "embedding": null
}
```

### Keyword

`keyword` is the human-readable concept, such as `AFL`, `footy`, or `Australian rules football`. Wording does not need to be identical across identities; concept embeddings let the matcher find semantically close phrases.

### Kind and kind embedding

`kind` describes what sort of concept the preference represents, for example `interest`, `value`, or `boundary`. It references a vector in the identity's top-level `kind_vectors` map. The vector is generated from the kind label and its canonical natural-language description. This allows differently named kinds, such as `hobby` and `activity`, to be recognised as related.

Kinds are not required to match by exact string. The matcher compares their vectors in the kind semantic space. For example, an `interest` may be relevant to an `activity` even when those labels differ. Kind similarity helps determine whether two concepts should be compared; it does not replace concept similarity.

An identity file contains one vector per kind label, so all preferences of that kind within the identity refer to the same vector. Different identity files may carry different snapshots of a kind vector.

### Affinity

`affinity` is a signed numeric value in the range `-1.0` to `1.0`:

```text
+0.9 = strongly attracts the persona
+0.5 = moderately attracts the persona
 0.0 = neutral or not specified
-0.5 = moderately repels the persona
-0.9 = strongly repels the persona
```

JSON numbers do not allow an explicit leading `+`, so positive values are written as ordinary positive numbers, such as `0.9`; negative values include `-`. Persona text may display the sign explicitly. Affinity is not semantic similarity: it records this person's stance toward the concept.

Boundaries and deal-breakers can be represented as repelling preferences with negative affinity. A shared repellent can be an alignment, while attraction by one person and repulsion by the other is a conflict.

Interpret pair alignment from both affinity signs:

| Person A affinity | Person B affinity | Pair result |
| --- | --- | --- |
| Positive | Positive | Positive alignment from shared attraction |
| Negative | Negative | Positive alignment from shared aversion |
| Positive | Negative (or vice versa) | Negative raw signal, discarded for discovery |
| Either is zero | Any value | No signal from this pair |

Shared attraction should normally rank ahead of shared aversion when selecting suggested topics. Shared aversion is still potential common ground and can be suggested lower in the list when context makes it natural. A boundary kind is not automatically excluded from topic suggestions, but any suggestion must respect the interaction context and applicable privacy or sensitivity controls. A positive result from two negative affinities means agreement in avoidance, not attraction to the avoided concept.

### Embeddings

`embedding` is the fixed-length vector for the keyword or phrase. The corresponding kind vector is looked up by `kind` in the identity's `kind_vectors` map. Vectors used in a comparison must have the same dimensions and compatible generation methods.

The current sample profiles use model metadata `qff-synthetic-rule-based`, version `1.0`, with 16 dimensions. Their vectors use coarse hand-authored topical axes plus deterministic keyword variation. They are normalized so cosine-similarity and signed-affinity calculations can be exercised, but they do not capture the quality or nuance of a trained embedding model. Treat their scores as simulation behavior only.

When a real embedding model is selected, regenerate concept and kind vectors with that model and version. Do not compare the synthetic vectors with real-model vectors.

## Persona model

```json
{
  "persona": "outdoor activity friend",
  "preferences": [
    {
      "keyword": "moderate hiking",
      "kind": "interest",
      "affinity": 0.8,
      "embedding": null
    },
    {
      "keyword": "reckless outdoor activities",
      "kind": "boundary",
      "affinity": -0.9,
      "embedding": null
    }
  ]
}
```

The preference entries are authoritative. Persona vectors, if later useful for broad candidate retrieval, are derived data and should not replace the individual preferences.

## Portable identity files and BASE consistency

Each identity property file carries its own `embedding_model`, `personas`, concept vectors, and `kind_vectors` map. A matcher can load and use one identity file without requiring a central kind-vector registry. This keeps identity files portable across independent matchers and supports offline use.

The kind-vector map follows BASE rather than global ACID consistency:

- **Basically available:** a matcher can use the kind-vector snapshot in the identity file it has, even when other copies or services are unavailable.
- **Soft state:** kind vectors may change when a kind description or embedding generation is refreshed.
- **Eventually consistent:** independently held identity files or matcher caches may temporarily contain different kind vectors; updates can propagate and converge later. Identical vectors are not guaranteed at every instant.

The `embedding_model` metadata identifies the vector space of each snapshot. A matcher must not calculate cosine similarity between incompatible model versions or dimensions. If kind vectors are incompatible, the matcher can still use the portable concept data, but should mark kind similarity unavailable or defer that comparison rather than treating incompatible vectors as comparable.

Example identity-level layout:

```json
{
  "identity_id": "example-identity",
  "embedding_model": {
    "name": "example-vector-model",
    "version": "example",
    "dimensions": 2
  },
  "personas": [
    {
      "persona": "outdoor activity friend",
      "preferences": [
        {
          "keyword": "moderate hiking",
          "kind": "interest",
          "affinity": 0.8,
          "embedding": [0.1, 0.2]
        }
      ]
    }
  ],
  "kind_vectors": {
    "interest": [0.3, 0.4],
    "activity": [0.31, 0.39]
  }
}
```

The shortened vectors above only illustrate the layout; stored vector lengths must match the declared model dimensions.

## Simple attract/repel matching

For two preferences, compare concept similarity and kind similarity separately. Each similarity is a value from `0.0` to `1.0` derived from vector similarity. Only compare pairs whose kind similarity indicates they are meaningfully related.

A simple pair contribution is:

```text
contribution = concept_similarity * kind_similarity * affinity_a * affinity_b
```

Same-sign affinities produce positive raw signals, including shared attraction and shared aversion. Opposite-sign affinities produce negative raw signals; zero affinity produces a zero signal. The matcher retains only positive raw signals and discards zero or negative signals completely before calculating persona alignment. A discarded disagreement is treated as no opinion: it is not shown, does not reduce a persona score, and is not included in aggregation denominators. Thus the resulting persona score measures positive shared ground, not overall compatibility.

Aggregate retained positive pair signals across relevant preference pairs to estimate persona alignment. If a preference has no retained positive signals, it contributes no match evidence and is excluded from the average. If a persona pair has no retained positive signals, it produces no discovery match. The exact aggregation and thresholds can be tuned later without changing the stored preference schema.

This is deliberately a simple similarity-and-polarity model; a high score alone does not imply trust, safety, or consent.

## Stored and derived data

Store:

```text
identity id
persona name
preference keyword or phrase
preference kind
signed affinity
concept embedding
identity-level kind vectors
embedding model name, version, and dimensions
```

Derive or cache as needed:

```text
kind-to-kind similarity (cacheable per compatible vector snapshot)
concept-to-concept similarity
persona-to-persona alignment
identity-pair match result and timestamp
```

Vectors from different model names, versions, or generation methods should not normally be compared directly. Regenerate concept and kind vectors when changing models, then propagate updated identity files or caches according to the BASE consistency policy.

## Design principles

- Keep concepts explicit and explainable; embeddings supplement them rather than replacing them.
- Keep kind similarity separate from concept similarity and affinity; store each kind vector once per identity.
- Use signed affinity for attraction or repulsion; do not encode polarity into the embedding.
- Treat all example affinities as provisional until confirmed by the person.
- A match result should expose only information the recipient is permitted to see.
