# Plan: Dashboard Quest Integration and Security

## Goal and boundaries

Implement [Dashboard Access to the Quest Backend](Decisions/002-dashboard-quest-backend-access.md): host the existing Dashboard Node.js server on Azure App Service, not Azure Functions. The server instantiates the Quest backend in its own process and accesses its data internally, without adding an API security bypass. The Dashboard viewer and Agent Chat use the Dashboard service over HTTP. The service and Quest backend have direct database access on the internal network.

Agent execution flow: the LLM proposes an action; server-side Agent Chat validates it and calls a Dashboard HTTP endpoint. That endpoint invokes the imported Quest functions in the Dashboard server process. Agent Chat runs server-side, not in the web browser. The browser displays the Dashboard and sends user commands; neither the browser nor the LLM directly invokes Quest functions or accesses the databases. Agent-scoped restrictions apply to these server-side operations.

Dashboard access is secured by its hosting platform and restricted to a cleared person authorized for full administrative access. Hosting security is an accepted dependency, configured and verified independently of this plan; it is not a prerequisite task for the Dashboard code changes. The application currently does not differentiate UI user permissions; an admitted UI user has full Dashboard access. Agent-scoped data restrictions remain separate from UI user permissions.

For local development, the local user is deemed to have full Dashboard access. Keep the local listener bound to loopback; this development assumption does not grant access to remotely reachable or deployed instances and does not require AuthDev or mocked Quest tokens. Agent-scoped restrictions still apply.

Hosting will use restrictive scaling and automatic shutdown to protect against runaway costs. Hosting configuration, scaling, shutdown and cost management are handled independently and are outside this implementation plan.

Hosting example: Linux P0v4, one instance, four hours/day may cost less than AUD 30/month if paid plan capacity is provisioned only for those hours. This is an illustrative estimate, not a quote; database, storage and LLM costs are separate. Merely stopping the Dashboard app after four hours does not achieve four-hour/day plan billing.

This plan is based on the Q3 workspace currently imported by the Dashboard, not an assumption that all Quest variants share its implementation. It records an investigation and proposed work; it does not claim the changes have been implemented.

## Findings

1. **Viewer reads impersonate agents over HTTP.** [server.mts](viewer/server.mts) `getQuestionsForAgent` and `getAnswersForAgent` sign local JWTs from agent frontmatter and call Q3 using `QUESTION_URL`. The questions view, answers view and referee context share these functions. This is not in-process access and couples the viewer to a Quest API accepting locally signed tokens. The answer path first checks the selected agent's question list; preserve that person-scoped behavior unless a separate privileged view is explicitly designed.
2. **The Dashboard owns a local token signer.** [authDev.mts](service/authDev.mts) has a hard-coded fallback signing key. The viewer imports it directly; [agentChat.setup.mts](agentChat.setup.mts) also uses it for the agent harness. Q3's [DI initialization](../quest3Tier/func/di/diInit.mts) selects `Dev` or `Prod` authentication, and [Q3 authDev](../quest3Tier/func/service/authDev.mts) verifies locally signed tokens using its configured secret. AuthDev is intended only for local development and unit testing; the Dashboard should no longer use it. It is not a bypass added to production authentication. Do not copy or reuse the fallback key in a deployed environment.
3. **Some in-process repository access already exists, but identity handling needs attention.** [server.mts](viewer/server.mts) initializes Q3's Table repository for the network view. [Q3 repository](../quest3Tier/func/repository/table/repository.mts) supplies `findProfileByExternalId`, `getCombinationListByUser`, `getAnswerListByQuestionId` and `listFriends`. Profile repository methods use internal IDs, while the agent frontmatter and `/profile/me` use external IDs. The network view currently passes report profile IDs from the latter directly to `listFriends`; verify and correct that mismatch. The Table initializer uses module-global settings and clears its client cache on reinitialization, so initialize once per process with the intended database configuration. It also creates tables on access; account for the necessary permissions and side effects.
4. **API answer and question authorization needs independent review.** [GetAnswerListByQuestionId.mts](../quest3Tier/func/handler/answer/GetAnswerListByQuestionId.mts) fetches answers without checking the caller's access to the question and returns each answer's external profile ID. [GetQuestionById](../quest3Tier/func/handler/question/getById.mts) also reads by ID without a caller visibility check. [AddAnswer](../quest3Tier/func/handler/answer/AddAnswer.mts), [ShareQuestion](../quest3Tier/func/handler/share/ShareQuestion.mts), [ShareQuestionCmd](../quest3Tier/func/handler/share/ShareQuestionCmd.mts), and the [question update](../quest3Tier/func/handler/question/patchById.mts) paths likewise require authorization review; the Table repository checks existence but does not establish ownership or visibility on those paths. The lack of repository-enforced RBAC and record-level access control is a security finding, not the intended long-term design. The current [route contract test](../quest3Tier/func/vitest/routeContract.test.mts) explicitly expects external answer IDs. These observations do not establish that the Dashboard caused the current behavior.
5. **Historical experiment changes affected the API.** Git commit `af6ccd0c` introduced a gated `experiment/human-session` endpoint that returned a locally signed human token, and also added question-access checks and owner/respondent answer filtering. The current Q3 route does not register that experiment endpoint, and the current answer list handler does not apply those historical checks. Commit `a2ef5806` changed the then-current answer-list handler to return external IDs; it did not itself introduce the missing visibility check. Confirm the intended current privacy policy before restoring historical filtering; do not reintroduce the experiment login or replace it with another API bypass.
6. **Agent Chat's Quest HTTP integration is legacy.** [agentChat.run.mts](agentChat.run.mts) currently makes signed HTTP calls to Quest as each agent, records API outcomes, and is instructed to test user-facing privacy and security. Replace this path with calls to the Dashboard service hosted on App Service, which instantiates Quest in-process. The service must distinguish privileged observation from agent-scoped operations so privileged data does not leak to agent prompts or memory. Agent Chat will no longer test the external Quest HTTP boundary through its normal interactions; retain that coverage in separate authenticated Quest API tests. [server.mts](viewer/server.mts) currently launches the harness as a child process and requires a Q3 API on port 7073.
7. **Keep the Dashboard UI and HTTP service in one codebase.** [server.mts](viewer/server.mts) already serves web pages, assets or data depending on the requested route. Import the Quest service into this Dashboard codebase and initialize it in-process; do not introduce a separate Dashboard backend or another internal HTTP hop. Separate the UI and HTTP service later only if needed. The current listener binds to loopback and uses origin checks on some mutations. The join and human-event routes receive a browser-supplied profile ID; [AgentLabJoin.tsx](../questUi/components/AgentLabJoin.tsx) supplies that ID. Hosting-platform security is handled independently, as described above.
8. **Current tests and documentation encode the old integration.** The server `--check` asserts outgoing bearer requests; [viewer-questions.mts](viewer/viewer-questions.mts) labels the source as Quest HTTP APIs. [Dashboard README](README.md) and [viewer architecture](viewer/architecture-overview.md) describe API-based operation, including some outdated paths. These need to match the final split between internal observation and API testing.
9. **LLM configuration is currently distributed.** [agentChat.llm.mts](agentChat.llm.mts), the viewer and launcher scripts load or pass Dashboard settings separately. The Dashboard's `local.settings.json` must select the LLM for local execution, whether internet-based or locally running; equivalent App Service application settings provide deployed configuration. The service's runtime configuration should be the source used by Agent Chat and Dashboard LLM operations.

## Implementation plan

1. **Establish the API baseline first.** Review the historical `visibleAnswer` / `visibleAnswers` behavior and current product privacy requirements, including who may see answers and author identity. Add focused Q3 route tests for unauthenticated callers, owner, shared recipient and unrelated user, including answer detail/list and write operations. Restore or implement the approved authorization at the Quest API/domain boundary, without any Dashboard-specific header, token, endpoint or configuration bypass. Update the external-ID contract test only to reflect the approved privacy behavior. Ensure the API cannot be made privileged by client-supplied profile IDs.
2. **Initialize Q3 within the Dashboard Node.js server.** Retain the existing HTTP server and provide focused operations for the viewer and Agent Chat; keep the application compatible with the independently managed App Service hosting. Reuse the existing `quest3Tier` workspace dependency and Table repository initializer in the Dashboard server process rather than calling the Quest Functions HTTP host, importing its `route.mts`, or registering its API auth provider. Initialize once per process with explicit storage settings; surface configuration and initialization failures. Resolve each agent's external ID using `findProfileByExternalId`, report missing profiles clearly on reads, and pass internal IDs to repository operations. Preserve any necessary profile-creation behavior for agent setup as an explicit operation, not a read side effect.
3. **Use imported Quest logic in the existing Dashboard routes.** Keep the UI and HTTP service together: the browser continues calling existing Dashboard routes, while their server-side implementation calls the imported Quest service in-process instead of Quest HTTP with generated tokens. Use `getCombinationListByUser(internalId)` and adapt its output to the existing Dashboard response shape. For answers, verify the selected person's question is in that person's owned/shared list before `getAnswerListByQuestionId`; preserve the question-ID mismatch check, `isEdited`, answer display labels, omission of raw answer `profileId`, and explicit errors. Resolve known participant external IDs to internal IDs for author labels; unknown authors remain unknown. Translate only the IDs needed for the existing viewer contract, and avoid exposing internal IDs to agents or browsers accidentally. Use the same service operations for referee reads and preserve activity enrichment. Correct `getRunNetwork` to resolve report external IDs before `listFriends`, including historical reports and missing profiles. Defer splitting the Dashboard UI and HTTP service until a concrete need arises.
4. **Move Agent Chat to the Dashboard service.** Replace agent calls to the Quest HTTP API with narrowly defined Dashboard HTTP operations backed by Quest in-process. Preserve agent-scoped visibility, permitted actions, validation, write budgets, correlation IDs, failure reporting and live chat behavior; do not pass privileged observer responses into agent prompts or memory. Preserve needed profile, friendship, question, answer, share and follow-up behaviors using Quest backend logic, not a generic HTTP proxy. Remove Dashboard use of `authDev`, including the harness signer, and remove `jsonwebtoken` if it is no longer needed. Never introduce a production signing secret or Quest API impersonation feature. Test the external Quest API separately using authenticated clients.
5. **Configure LLM selection in the Dashboard service.** Use its `local.settings.json` `Values` as the local source of provider, model and endpoint configuration for both Dashboard and Agent Chat LLM operations. Reuse the existing providers for internet-based and local models, preserving their readiness checks and inference concurrency behavior. Keep credentials out of source control; use equivalent App Service application settings or environment variables outside local development. Fail visibly for invalid or unavailable configuration.
6. **Preserve application integration boundaries.** Rely on the independently managed hosting security; do not add differentiated UI user roles or hosting-security implementation and verification tasks here. Enforce agent-scoped operations so agents do not inherit the UI administrator's unrestricted observations. Preserve the association between each agent and its execution context rather than treating an arbitrary actor ID as proof of identity. Do not expose arbitrary Quest backend operations or introduce a bypass of Quest API protections. Keep privileged Dashboard routes read-only where they are today, preserve validation and origin protections, and protect database and LLM credentials. Keep test reset operations restricted to verified local Azurite.
7. **Update startup, UI and documentation.** Viewer and Agent Chat operations must work through the Dashboard service when the Quest HTTP service is stopped, with the configured database available. Replace the legacy Quest port readiness check with Dashboard service readiness checks. Update technical source labels, README, architecture diagram and startup instructions to distinguish Dashboard HTTP, in-process Quest access, separate API tests and Activity data. Preserve existing Dashboard response shapes and run behavior unless an intentional change is documented.

## Verification and acceptance

- Add focused Dashboard tests for owned/shared question visibility, denial for an unrelated question, answer labels and edited flags, unknown/missing participant profiles, mismatched question IDs, external-to-internal ID resolution including network paths, and explicit storage failures.
- Verify viewer question, answer, network and referee reads and Agent Chat operations work through the Dashboard service against a disposable database while the Quest API is stopped; assert neither client calls Quest HTTP or mints Quest tokens. Confirm repeated requests do not reconfigure the shared repository.
- Exercise the API separately with valid and invalid identities: missing/invalid tokens are rejected, unauthorized users cannot read or modify another user's protected data, permitted users retain intended access, and no experimental login or Dashboard bypass exists. Cover API response privacy, not just Dashboard filtering.
- Verify Dashboard configuration selects both a local and an internet-based LLM provider using appropriate mocks or available test services, and reports missing or invalid settings without exposing secrets.
- Run the targeted Dashboard and Q3 tests and builds, including `pnpm --dir module/dashboard run build`, the updated Dashboard `--check`, and the Q3 route-contract tests. Run a local end-to-end smoke test with disposable data and document any unavailable dependencies or credentials.

## Decisions confirmed

No further policy decision is needed before implementation. As specified in step 4, preserve existing agent-scoped visibility, permitted actions, validation, write budgets, correlation IDs, failure reporting and live chat behavior through Quest backend logic. Privileged Dashboard observer responses must not enter agent prompts or memory. Hosting security, scaling, shutdown and costs are handled independently and are outside this implementation plan.
